# QA

## Key Ideas

- **Quality Evidence**: QA gathers proof that the work behaves as intended.
- **Project Specific**: QA should use project Quality tests, guidance, and governance.
- **Failure Is Useful**: failed QA should create actionable evidence, not just block progress.

## Purpose

QA exists to turn confidence into evidence. Refine should make agent-produced work accountable through tests, checks, diagnostics, review aids, and other target-app verification.

## Expected Role

QA should connect workflow to the Agents capability's quality, governance, logs, and evidence behavior. It should record what ran, what passed, what failed, and what should happen next.

QA should be flexible. Some apps need automated tests, some need build checks, some need visual inspection, and future agents may generate targeted verification for the Goal.

## What Happens

When a Goal is in QA:

- Refine gathers quality evidence for the change.
- The configured agent evaluates every project Quality test against the exact registered isolated Goal candidate for `pre_merge`, or against the exact integrated target checkout for `post_build`, deciding how to run each plain-text test. Reconciliation uses the same integrated-target identity with its distinct reconciliation scope.
- Each test requires a command. Refine correlates the requested command with a supervised execution and records its process ID, exit code, output evidence, and final pass or fail.
- Checks should run through shared Process and Agents capabilities where commands or agents are involved.
- Workflow and manual Goal checks use the same exclusive Goal/candidate operation and write the same exact Goal-round Quality fields and log shape.
- A cleanup-visible candidate handoff owns the worktree from materialization through implementation, Governance, and publication. For pre-merge QA, workflow registers the exact Quality commitment and durably enters QA before settling that handoff; cleanup must therefore observe either owner at every boundary. For post-build QA, the handoff is retained through Ready Merge and settled only after exact integration evidence exists.
- Quality verifies the committed Goal Round, scope, branch, path registration, evaluation commit, HEAD, index, and checkout before and after evaluation without cleaning or resetting detected work. Integrated-target scopes validate source candidate plus target integration and do not depend on a legitimately retired candidate worktree.
- Results should attach to the Goal as evidence: what ran, what passed, what failed, and what risk remains.
- Exact Goal-round fields and the Goal log must be durable before a Quality operation reports success or failure; persistence failures leave that local operation nonterminal for restart recovery. Cancelling a Quality operation also remains nonterminal until every process launched by that operation is confirmed exited. This is separate from terminal Goal cancellation.
- Passing QA should move the Goal toward review or completion according to workflow rules.
- Failing QA should preserve output and create a recovery path rather than losing the failed attempt.
- Candidate infrastructure loss is not a failed Quality test. Before launch it records `quality_candidate_infrastructure` on workflow while Quality remains unclassified and no result is created; after operation registration it additionally settles that operation with `quality_candidate_infrastructure_fault` and retains observed logs. Refine must not recreate, reset, remove, or otherwise repair the missing checkout in place. Shell parsing failures alone use `quality_command_harness_fault`.

The authoritative Quality timing controls ordering: `pre_merge` runs QA against the isolated candidate before Ready Merge, while `post_build` runs QA against the integrated target after Ready Merge and the optional rebuild. The candidate round pins that choice when validation begins, and every later stage or retry reads the pinned choice rather than mutable project settings. Provider, parsing, cancellation, and restart-interruption outcomes remain visible instead of being converted to generic success or hidden retries; provider and test launches recheck their local Quality operation before starting. Restart recovery uses the target-app and Refine-state identity stored on that local operation, independent of whichever app is currently selected.

## Future Direction

Future QA should become more agentic: generated tests, screenshot comparison, semantic checks, dependency analysis, risk scoring, and evidence summaries. The state should remain the workflow point where proof is gathered.
